# Ash/Spark/AshPostgres/Igniter Gotchas

A collection of non-obvious behaviors, undocumented internals, and landmines
encountered while building a schema-diffing tool, an application-level DSL,
a custom admin UI, and a project generator on top of Ash. Each entry cost
someone real debugging time; the goal here is that it costs you less.
Verified against the Ash/AshPostgres/Spark/Igniter versions pinned in this
project's `mix.lock` at the time of writing (Ash 3.32, AshPostgres 2.12,
Spark 2.7, Igniter 0.8) — upstream behavior may have changed since.

## Ash resources & policies

**`Spark.implements_behaviour?(mod, Ash.Resource)` returns `false` for real resources.**
`Ash.Resource` isn't a classic `@behaviour` — it's implemented as a Spark DSL
extension, so the behaviour check never matches, even against a module that
does `use Ash.Resource`. Use `Ash.Resource.Info.resource?/1` instead (it
delegates to `Spark.Dsl.is?/2` internally).

```elixir
Ash.Resource.Info.resource?(MyApp.Account)  # true
Spark.implements_behaviour?(MyApp.Account, Ash.Resource)  # false, always
```

**Policy `access_type` defaults to `:filter`, which turns unauthorized reads into silent empty lists.**
`policy always() do authorize_if actor_present() end` protects `create`/
`update`/`destroy` with a raised `Ash.Error.Forbidden` when there's no actor,
but `read` actions default to `access_type :filter` — an unauthorized read
returns `{:ok, []}`, not an error. A test that only asserts "no exception" or
a UI that treats an empty list as "no data yet" will both hide a policy hole.
Add `default_access_type :strict` to the resource's `policies` block if you
want reads to behave the same as writes.

**`Ash.can?/3` can return `:maybe`, which is treated as `true`.**
For gating a New/Edit/Delete button, `Ash.can?({resource, action}, actor)` is
cheap when policies are pure actor-presence checks (no DB query needed).
But its docs are explicit: a policy with a runtime-dependent check (e.g. one
that needs the record's actual field values) returns `:maybe`, and `can?/3`
treats that as `true`. A button can therefore be visible and still get
rejected at submit time — button visibility is not a submission guarantee,
just a cheap first filter.

**Pagination requires the `read` action to opt in — otherwise it's `PaginationRequired`.**
`Ash.read(resource, page: [limit: 25, offset: N])` raises
`Ash.Error.Invalid.PaginationRequired` unless the resource's `:read` action
declares `pagination offset?: true` (or similar). If you can't touch the
resource definition (e.g. it's generated by a codegen layer you don't
control), fall back to plain `Ash.Query.limit/2` + `Ash.Query.offset/2` —
these work on any read action without a `pagination` declaration, at the
cost of losing `Ash.Page.Offset`'s built-in `count`/`more?`.

**`Ash.sum/3` returns `{:ok, nil}` on an empty result set, not `{:ok, 0}`.**
Displaying a sum aggregate directly will render a blank instead of `0` the
first time a table has no matching rows. Normalize explicitly:

```elixir
case Ash.sum(query, :amount, actor: actor) do
  {:ok, nil} -> {:ok, 0}
  other -> other
end
```

**`Decimal` values don't implement `Phoenix.HTML.Safe`.**
A raw `Decimal` struct returned by `Ash.sum/3` (for a `:decimal` attribute)
can't be interpolated directly into a LiveView template (`{@value}`) —
convert with `to_string/1` or a formatter function before rendering, or you
get a `Protocol.UndefinedError` the first time real decimal data flows
through.

**A `belongs_to`'s foreign key is just a plain attribute — there's no automatic option list.**
`Ash.Resource.Info.attributes/1` shows a `belongs_to :account`'s
`account_id` as an ordinary `:uuid` attribute; nothing marks it as
"this references another resource, offer a dropdown." If you're building
generic form/table rendering over arbitrary resources, you have to cross-
reference `Ash.Resource.Info.public_relationships/1` (matching on
`source_attribute`) yourself to know which attributes are actually foreign
keys.

**`AshAuthentication` policy bypasses require a specific private context flag — tests need to set it explicitly.**
A resource with
`policies do bypass AshAuthentication.Checks.AshAuthenticationInteraction do ... end end`
will reject a plain `Ash.Changeset.for_create(:register_with_password, attrs)`
call in a test with `Forbidden`, because the bypass only activates when
`changeset.context.private.ash_authentication?` is `true` — a flag normally
set internally by `AshAuthentication.Strategy.action/4`. To exercise the
action directly in a test, pass it yourself:

```elixir
Ash.Changeset.for_create(:register_with_password, attrs,
  context: %{private: %{ash_authentication?: true}}
)
```

## Ash queries

**`Ash.Query.filter/2` is a macro — it can't take a runtime list of field names.**
`Ash.Query.filter(query, expr(contains(name, ^term) or contains(email, ^term)))`
only works when the fields are known at compile time; `^field_atom` pins a
*value*, not a field reference, so you cannot parameterize which attribute
gets filtered. For a dynamic OR-across-fields search, use
`Ash.Query.filter_input/2`, which takes a plain runtime keyword/map
structure instead of an AST:

```elixir
fields = [:name, :email]
Ash.Query.filter_input(query, or: Enum.map(fields, &{&1, [contains: term]}))
```

**Case-insensitive `contains` is `Ash.CiString.new/1`, not manual downcasing.**
`contains/2` has an overload for `Ash.CiString` — wrap the *search term*
(not the field) and comparisons ignore case automatically:

```elixir
Ash.Query.filter_input(query, name: [contains: Ash.CiString.new(term)])
```

**`filter_input/2` (and the search patterns built on it) only sees `public? true` attributes.**
An attribute or relationship left at the default `public? false` is
invisible to user-input-driven filtering — this also affects any DSL
verifier you write that checks "is this a filterable field" via
`Ash.Query.filter_input`-compatible mechanisms; check `public?` explicitly
rather than assuming any declared attribute qualifies.

**Duplicate-detection via `GROUP BY ... HAVING count(*) > 1` disagrees with Postgres `UNIQUE` semantics on NULLs.**
Postgres `UNIQUE` constraints treat NULL as "distinct from every other value,
including other NULLs" — multiple NULL rows don't violate uniqueness. A
naive `GROUP BY col HAVING count(*) > 1` groups multiple NULLs together as a
false-positive duplicate. Add `WHERE col IS NOT NULL` before grouping if
you're trying to mirror what a real UNIQUE constraint would flag.

## Spark DSL & macros

**`use Ash.Resource` (or any DSL-defining `use`) must expand at its normal position inside `__using__` — don't defer it to `@before_compile`.**
Wrapping the whole generated resource body (including `use Ash.Resource`)
and injecting it from `@before_compile` compiles fine in isolation
(`Ash.Resource.Info.resource?/1` on the final module returns `true`), but
breaks under `mix compile --warnings-as-errors` for any *other* module that
references it (a `belongs_to` pointing at it, a domain listing it in
`resources do ... end`). The failure shows up as
`ArgumentError: ... is not a Spark DSL module` inside Elixir's
`Module.ParallelChecker` cross-module verification, because the module
isn't recognized as an Ash resource until much later in compilation than a
hand-written one would be. Fix: run `use Ash.Resource, ...` immediately in
`__using__`, at the same position a hand-written resource would have it.
Reserve `@before_compile` for things that only need to run *after* the DSL
body is collected — e.g. a guard that raises if a required block was never
invoked.

**Module attributes set as generated code vs. set as a macro-expansion side effect are visible at different times.**
`quote do @my_attr unquote(value) end`, spliced into a module body, only
becomes readable via `Module.get_attribute/2` once that generated code
actually *runs* as part of the module — a macro expanding *earlier* in the
same module (e.g. a nested DSL macro trying to read options stashed by an
outer `use`) will see `nil`. Calling `Module.put_attribute/3` directly, as
Elixir code executed *during* macro expansion (not as quoted code to be
compiled later), makes the value visible to macros expanding immediately
afterward in the same module.

**Combining an inline keyword-opts argument with a `do...end` block on a custom entity macro is an arity trap.**
`workflow :name, resource: X, field: :y do stages([...]) end` looks like it
should call a 2-argument entity macro (`name`, `opts`) with a block, but
Elixir's `do...end` sugar always appends the block as a *separate* final
argument: this compiles to `workflow(:name, [resource: X, field: :y], [do: block])`
— three arguments. A Spark entity macro generated from `entity.args` has an
arity of `length(args) + 1`, so a two-arg entity (`name`, `opts`) has no
3-arity clause and you get `undefined function workflow/3`. This is the same
reason `create :new, accept: [...] do ... end` doesn't work as a plain Ash
action macro either. There's no way to have both inline keyword options
*and* a `do` block on the same call — pick one: either all-keyword
(`workflow :name, resource: X, stages: [...]`) or wrap everything as a block.

**`Spark.InfoGenerator`'s naming convention may not match the public API you want.**
`Spark.InfoGenerator` derives function names from the DSL section path (a
`name` option inside an `app` section becomes `app_name/1`). If your target
API is unprefixed (`MyDsl.Info.name/1`), it won't fit, and there's no
override — the escape hatch is to hand-write the Info module the way
`Ash.Domain.Info` does it: call `Spark.Dsl.Extension.get_opt/3` and
`get_entities/2` directly. It's normally a handful of lines per accessor.

**Entities that should repeat without a wrapping section block need `top_level?: true`.**
By default a Spark `%Spark.Dsl.Section{}` requires its entities to be
wrapped (`section_name do entity ... end`). To allow
`workflow :sales do ... end` directly at the top level of a DSL body (no
`workflows do ... end` wrapper), set `top_level?: true` on the section —
keeping the section name (`:workflows`) distinct from the entity name
(`:workflow`) so `Info.workflows/1` still reads naturally.

**Entity target structs need a `__spark_metadata__` field, or `--warnings-as-errors` fails on a deprecation warning.**
Spark 2.7+ expects every `%Spark.Dsl.Entity{target: MyStruct}` struct to
carry a `__spark_metadata__` field for source-location annotations; omitting
it produces "Entity without `__spark_metadata__` field is deprecated" for
every entity target, which becomes a hard failure under
`--warnings-as-errors`. Add the field to each entity's `defstruct`.

**`Spark.Test.assert_dsl_error/2` is the tool for testing that a DSL *fails to compile*.**
Verifier errors fire from an `@after_verify` hook, which a normal
`assert_raise` can't catch (Spark converts them to a stderr warning by
default instead of raising in-process). `Spark.Test.assert_dsl_error` lets
you `defmodule` a broken DSL usage inline inside the assertion block and
pattern-match on the collected `%Spark.Error.DslError{}` — no manual
`try/rescue` or subprocess needed.

## AshPostgres & migrations

**`AshPostgres.MigrationGenerator.get_migration_type/2` is public and reusable — but pass the attribute's full `constraints`, not just the bare type.**
This is the same function AshPostgres itself uses to turn an Ash type into
an Ecto migration type, and it's safe to call directly instead of
reimplementing the mapping. But `get_migration_type(Ash.Type.UtcDatetimeUsec, [])`
(empty constraints) returns `:utc_datetime`, indistinguishable from the
non-usec type — only passing the attribute's actual `constraints` (e.g.
`precision: :microsecond`) yields `:utc_datetime_usec`. Passing "the type
for now, constraints later" silently collapses distinct types.

**The Ecto migration type and the real Postgres column type are two different naming systems.**
`get_migration_type/2` returns Ecto's migration-DSL type, not what
`pg_catalog`/`information_schema` reports as the column's real type
(`udt_name`). Known divergences: `:map` → `jsonb`, both `:utc_datetime` and
`:utc_datetime_usec` → `timestamp`, `{:decimal, _, _}` → `numeric`. Building
a Desired-vs-Actual schema comparison means maintaining this second mapping
yourself (Ecto's own converter for this is a private function).

**FK constraint names and unique-index names have a default naming convention, but it's not exposed as a public function.**
`AshPostgres.DataLayer.Info.foreign_key_names/1` and
`identity_index_names/1` only return *overridden* names — when nothing is
overridden, the actual default (`"#{table}_#{attribute}_fkey"`,
`"#{table}_#{identity_name}_index"`) has to be reconstructed by hand from
reading the migration generator's source, since it isn't part of any
documented public API. Get this wrong and a clean, unmodified schema will
show phantom "constraint renamed" diffs.

**AshPostgres's resource snapshot JSON format is an internal implementation detail with no compatibility guarantee.**
`priv/resource_snapshots/repo/<table>/<timestamp>.json` (written by
`mix ash.codegen`) has a stable-enough structure in practice
(`attributes[].source`, `attributes[].type`, `table`, `hash` — parseable
with plain `Jason.decode!/1` + `Map.get/2`), but there is no documented
schema and no compatibility promise. Code that parses these files directly
(e.g. for rename detection across history) should expect an AshPostgres
upgrade to be a potential breaking change, and should have tests that read
real generated snapshot files as a canary.

**Ash resource defaults and DB column defaults are different kinds of values — don't string-compare them.**
An attribute's `default` in Ash code is often a function reference
(`&Ash.UUID.generate/0`, `&DateTime.utc_now/0`) or a plain literal
(`:lead`); the *database's* actual default expression
(`gen_random_uuid()`, `(now() AT TIME ZONE 'utc'::text)`) is a SQL string
chosen independently by the migration generator — the two don't correspond
character-for-character. Comparing them as text produces false-positive
drift. Normalize both sides into a small closed set first (e.g. "generated
dynamically" vs. "literal value X" vs. "none") and compare *that*, not the
raw expressions.

**Timestamp precision isn't visible from the column's type name alone (`udt_name`) — you need `information_schema.columns.datetime_precision`.**
Postgres reports both `timestamp(0)` and `timestamp(6)` as the same
`udt_name` (`"timestamp"`); only `datetime_precision` distinguishes them.
In practice, given how AshPostgres generates migrations: `:utc_datetime` /
`:naive_datetime` / `:time` are hardcoded by Ecto's Postgres adapter to
`timestamp(0)` (no precision option even exists for them), while `_usec`
variants get no explicit `precision:` from AshPostgres and fall through to
Postgres's own default precision of 6. So in current versions there are
really only two precisions that occur in the wild — but detecting a
precision *change* at all requires reading `datetime_precision` in
addition to the type name.

**`Ash.Type.NaiveDatetimeUsec` doesn't exist — `NaiveDatetime` and `UtcDatetime` are not symmetric.**
`UtcDatetime`/`UtcDatetimeUsec` are separate Ash type modules, but
`Ash.Type.NaiveDatetime.storage_type/1` always returns `:naive_datetime`
regardless of constraints — there's no usec-variant module to select a
different storage type. Code written to handle both families symmetrically
will have an unreachable branch for the naive/usec combination.

**Quote every identifier in hand-built introspection/probe SQL — table and column names are not guaranteed to be simple.**
Names sourced from `pg_catalog`/Ash resource definitions (table names,
column names, identity field lists) can legally contain spaces, mixed case,
or reserved words. A read-only probe query built with plain string
interpolation breaks the moment it touches a column literally named
`"Group"`. A minimal identifier quoter is enough — double-quote and escape
embedded quotes:

```elixir
def quote_ident(name), do: "\"" <> String.replace(name, "\"", "\"\"") <> "\""
```

Centralize this in one function everywhere query strings are assembled;
scattering ad hoc interpolation across each query type means only one of
them needs to forget quoting to reintroduce the bug.

**Ash has no distinct "long text" type — `:string` is it.**
There's no Ash/Ecto type that maps to Postgres `text` as opposed to
`varchar(n)` other than via the `max_length` constraint on `:string`. A
`:text`-flavored convenience type built as sugar over `:string` generates
byte-for-byte identical Ash code to plain `:string` — it's naming sugar
only, not a distinct semantic type.

## Igniter

**Igniter 0.8.3's AST-based comment insertion silently drops comments in real projects.**
`Igniter.Code.Common.add_code/3` / `add_comment/3` (inserting a
comment-only string into a parsed AST) can look correct in a minimal
`mix run -e` reproduction but fails in a real module: for a single-child
module body it introduces a stray `nil` node, and for a multi-statement
module the inserted comment is dropped entirely. The cause is that
`Igniter.Project.Module.find_and_update_module!` routes the rewrite through
`Rewrite.Source.update(source, :quoted, ...)`, which re-renders via
`Code.quoted_to_algebra/2` (the standard formatter algorithm) rather than
`Sourceror.to_string/1` — and the formatter path doesn't understand
comments embedded only as node metadata. If you need to leave the user
actionable guidance instead of doing something automatically, don't try to
inject a `# TODO` comment into their file — use
`Igniter.add_notice/2` with a complete copy-paste snippet in the message
body instead. Untouched files also make idempotency trivial: nothing to
diff against, so a second run just prints the same notice again.

**A module existing doesn't mean it has the specific behavior you're relying on — verify the actual AST.**
Before auto-wiring against a convention (e.g. "if `MyAppWeb.LiveUserAuth`
exists, assume it exports an `on_mount(:current_user, ...)` clause and
mount against it"), check that the clause is actually present, not just
that a same-named module exists — a differently-implemented module with the
same name will otherwise get a silently wrong integration. Use
`Igniter.Code.Function.function_call?/2` plus `argument_equals?/3` to
confirm the AST really has the call you expect, and fall back to a manual
notice when it doesn't.

```elixir
Igniter.Code.Function.function_call?(zipper, :on_mount, [4]) and
  Igniter.Code.Function.argument_equals?(zipper, 0, :current_user)
```

**`mix igniter.new --yes` suppresses confirmation prompts in every composed sub-task, not just the top-level one.**
Running `igniter.new --with phx.new --install ash,ash_postgres,...` with
`--yes` (stdin redirected to `/dev/null`, as in a spawned subprocess) also
silences the child installers it composes (`ash.install`,
`ash_postgres.install`, etc.) without hanging. The one thing that still
prints is a genuinely informational `Igniter.add_notice` (e.g. a dependency
substitution suggestion) — that's not a prompt, so it doesn't block
completion even though it appears mid-run.

**When injecting code by anchor string, require the anchor to appear exactly once — don't silently skip or double-insert.**
Text-anchored injection into a generated file (e.g. finding
`"defp deps do\n    [\n"` to splice a new dependency after it) is fragile
against template changes. Make the injection fail loudly if the anchor
count isn't exactly 1 (missing anchor: template changed upstream; more than
one: ambiguous target) rather than guessing. A generator that fails with a
clear error when its assumptions break is safer than one that silently
produces a subtly wrong file. Pin the exact template output you depend on
as a fixture so a future upstream format change is caught by a test, not a
user's broken generated app.

## Phoenix LiveView

**HEEx silently disables `{...}` interpolation inside `<style>` and `<script>` tags.**
A component that embeds its own stylesheet with `<style>{css()}</style>`
compiles cleanly and every test passes — but the browser receives the
literal text `{css()}` as its CSS, so the page renders completely
unstyled. This is documented HEEx behavior (curly interpolation is off
inside `style`/`script`); the escape hatch is the EEx form:

```heex
<style>
  <%= Phoenix.HTML.raw(css()) %>
</style>
```

Because nothing raises, add a regression test that renders the component
and asserts a real CSS rule is present in the output (and that the
literal interpolation source is not).
